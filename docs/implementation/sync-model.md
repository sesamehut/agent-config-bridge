# 同步模型

## 模型目标

同步模型要支撑两件事。第一，用户长期只维护一份规范源。第二，用户仍然可以在 Claude
Code 或 Codex 的配置文件里工作；如果这些文件发生了可采纳的修改，工具需要识别出来，
并让用户明确选择是否写回规范源。

Bridge 通过目标工具 skill 执行同步流程。skill 规定读取、判断、出计划、确认和写入的步骤；
工具映射知识负责说明 Claude Code 与 Codex 的语义差异；git 负责提供 diff、历史基线和
回滚能力。

因此同步分为两条路径：

- 规范源 -> Claude / Codex：投射（hook 触发或用户调用 skill）。
- Claude / Codex -> 规范源：对账（按需调用 reconcile skill）。

两条路径保持分离。投射是常规写入，来源明确；对账用于回收人工修改，必须先确认相关目标
配置仍然可信。

## git 作为确定性底座

变更判断交给 git，不另建内容索引：

- **改了什么**：`git diff` / `git status`，精确到行。
- **上次同步态是什么**：git 历史作为基线，不另存基线快照。
- **未触发的漂移**：即使某些 Codex 侧改动没有 hook，`git diff` 仍能显示。
- **写错怎么办**：`git restore` 和历史记录提供回滚路径。

归属信号有两个来源：hook 触发本身携带“谁在哪个工具里改了什么”；受管区块标记表明“这段
内容由 Bridge 管理”。两者加上 git 历史，就足以判断归属与漂移。

这个模型要求投射出来的目标工具配置文件本身入 git。`CLAUDE.md`、`AGENTS.md`、
`.claude/` 等属于运行态配置：它们包含人工内容，也是 agent 实际读取的文件。真正进
`.gitignore` 的只有 Bridge 工具侧的构建中间产物。

## 规范条目

规范源里的每个条目都要能跨工具稳定识别，并且便于人工审阅和目标工具中的智能体处理。格式采用
markdown、轻量 frontmatter 和目录约定，不在 MVP 阶段引入完整 schema 校验层。

语义上至少包含：

- **条目 ID**：稳定、可读，跨工具投射时保持不变。
- **领域**：属于 `skills`、`rules` 还是 `hooks`。
- **内容**：工具无关内容，或一个需要整体投射的目录。
- **目标策略**：投射到哪些工具，是否允许某个工具有特化内容。

“上次写到哪、内容是否变了”由 git 历史和受管区块标记承担。

## skill 工作流

无论投射还是对账，Bridge skill 都遵循同一套流程。每一步默认借助目标工具和 LLM 的固有
能力，只有过窄门的确定性操作才交给代码（判据见[技术栈](../architecture/tech-stack.md)）：

1. **触发 / 调用**：投射由 hook 触发或用户调用；对账由用户按需调用。
2. **取证**：用 `git diff` / `git status` 读取实际变更（git）。
3. **判断意图**：对照规范源和映射知识给每个目标分类——已确定映射查表（代码），长尾语义
   由 LLM 判断。
4. **出计划**：说明会创建、更新、跳过、冲突或无法表达的内容。
5. **确认后落盘**：用户确认后，由目标工具自带 Read / Edit / Write 写入，且只动受管区块。
6. **收尾自检**：重读相关文件并比对 diff；逐字节比对与忽略空行 / 排序的归一化由代码完成，
   只有无意义变化时不写入。

## 意图分类

同步计划至少使用以下分类。它们是报告和确认用语，不需要设计成独立代码状态机：

- `create`：目标工具配置不存在，可从规范源创建。
- `update`：目标工具配置受管，规范源已变化，可更新。
- `unchanged`：规范源与目标工具配置一致，无需动作。
- `conflict`：规范源与目标工具配置文件相对上次同步态同时变化，需用户选择。
- `unsupported`：目标工具无法表达这个规范条目。
- 需采纳或替换：目标存在但没有受管标记，且看起来由用户手写，先问用户再决定。

## 输出稳定性：受管区块

重新生成文件时，最需要控制的是无意义 diff 和人工内容被覆盖。解决方式是把投射内容限制在
受管区块中，skill 只修改区块内内容，区块外逐字节保留：

```text
<!-- bridge:managed:start id=... -->
（由规范源投射的内容）
<!-- bridge:managed:end -->
```

这样工具特化的人工内容和 Bridge 投射内容可以在同一个文件里共存。`CLAUDE.md` 与
`AGENTS.md` 尤其依赖这一点：入口文件常有人工段落，投射只能落在受管区块里。落盘前的
diff 自检用于过滤空行、排序等无意义变化。

## 规范源厚度

规范源在不同配置面中的作用不同：

- **技能**：工具无关、整体复制，规范源接近一份母本。
- **规则 / 钩子**：语义发散、映射可能有损，需要规范源保存意图和各工具 delta。

下面三节分别说明技能、规则和钩子的处理方式，也对应[架构概览](../architecture/overview.md)
中规范源的职责。

## 技能

技能适合最先落地，因为 Claude Code 与 Codex 都能消费以 `SKILL.md` 为核心的技能目录。
规范技能是唯一可维护副本，包含 `SKILL.md`、脚本、资源和引用文件。投射时把规范技能整体
复制到各工具技能目录。

这里选择 copy，主要考虑 Windows、插件打包和 git diff 的稳定性。copy 的结果更容易审阅，
也更容易回滚。

只有带受管标记的目标工具技能副本才会被 skill 自动更新。用户直接改了目标工具技能副本时，
对账只能在规范源未变、目标工具中的差异可由 `git diff` 解释时进行。

## 规则 / 指令

规则比技能更容易误判，因为不同工具用相似名称描述不同能力：

- Claude Code 的 `CLAUDE.md` 与 `.claude/rules/*.md` 主要是面向智能体的指令。
- Codex 的 `AGENTS.md` 也是面向智能体的指令。
- Codex 命令审批 / 沙盒规则属于执行许可和沙盒控制，需要独立于 Claude 提示词规则建模。

规范规则应按语义拆分，例如项目概览、工作流规则、工具规则和工具特化附录。`CLAUDE.md`
与 `AGENTS.md` 由这些片段在受管区块里组合生成；如果某个项目暂时需要人工维护入口文件，
skill 也要能用 `git diff` 检测它们与规范规则的漂移。

只适用于 Claude Code 或只适用于 Codex 的要求应放入对应附录，确保投射的共用部分与实际
行为一致。

## 钩子

钩子是 MVP 中风险最高的配置面。难点主要在执行时机、权限、环境变量和失败语义：同样叫
钩子，在两个工具中可能代表不同生命周期点。

因此规范钩子描述意图，具体工具字段由映射知识处理。一个钩子条目应写清触发点、目的、
命令或脚本、环境要求和失败策略。某个意图在当前工具上是 `full`、`partial` 还是
`unsupported`，由工具映射知识判断，并显示在同步计划里。

部分映射必须以 `partial` 状态展示。高副作用钩子默认要求显式启用，让自动执行面的扩大
成为用户可见的选择。

## 护栏与写入规则

写入必须满足以下规则：

- 落盘前先给同步计划并取得确认；默认不自动写。
- 只改 Bridge 受管的文件集合，只动受管区块，区块外逐字节保留。
- 没有受管标记、看起来由用户手写的文件不覆盖，先询问采纳还是替换。
- 无法判断语义等价性时停止并要求用户确认。
- 依赖 git 作为安全网：落盘前确保工作区可追溯，写错能 `git restore`。

## 已知代价

这个方案的稳定性取决于运行 skill 的目标工具和模型版本，同一份 skill 在不同环境中的执行细节
可能有差异。设计上通过同步计划、受管区块、git diff、自检和用户确认来降低风险，没有把
所有判断提前写成同步引擎。
