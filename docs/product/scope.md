# 产品范围

## 要解决的问题

同一个项目同时使用 Claude Code 和 Codex 时，项目级配置通常会被拆成两套：
Claude Code 读取 `CLAUDE.md`、`.claude/rules/` 和技能目录，Codex 读取 `AGENTS.md`
和自己的技能目录。直接复制一份配置可以应急，但后续维护会变得不可靠：一侧修改后
另一侧容易遗漏，名字相近的工具能力也可能并不等价。

Agent Config Bridge 的目标是让项目维护一份可审计的规范源，再把这份规范源投射成
Claude Code 和 Codex 各自能直接读取的配置布局。如果用户确实在目标工具配置文件里做了
修改，工具需要把它识别为漂移，并通过明确的采纳流程决定是否写回规范源。

最终用户仍然按 Claude Code 和 Codex 各自的使用方式工作，但主要维护的是同一套技能、
规则和钩子约定。

## 面向用户

这个工具首先服务三类用户：

- 在同一个仓库里交替使用 Claude Code 与 Codex 的个人开发者。
- 希望把项目级智能体约定维护成一份，再提供给不同工具使用的仓库维护者。
- 已经有 Claude `skills`、`CLAUDE.md`、`.claude/rules/`，希望逐步迁移到
  Claude / Codex 共用约定的用户。

这些用户愿意接受一份规范源，但不希望放弃目标工具配置文件。Claude Code 仍然应该看到
Claude Code 习惯的入口和目录，Codex 也应该看到 Codex 习惯的入口和目录。

## MVP 范围

MVP 只处理项目级配置，先覆盖三类内容：

- **技能**：以技能目录为单位，包括 `SKILL.md`、脚本、资源和引用文件。
- **规则 / 指令**：面向智能体的项目说明、规则片段，以及 `CLAUDE.md` / `AGENTS.md`
  这类入口文件。
- **钩子**：按意图建模，例如触发点、目的、命令、环境要求和失败策略。目标工具表达能力
  不完整时，在同步计划中标成 `partial` 或 `unsupported`。

这个范围刻意保持小。技能最适合先验证单源投射模型；规则和钩子更容易遇到工具语义差异，
需要在投射和采纳流程稳定后再逐步展开。

## MVP 之外

MVP 不处理 MCP 服务器、智能体 / 子智能体、全局用户配置、权限模型、模型选择和第三方
IDE 规则。这些配置面的工具差异更大，需要独立设计。

Claude Code 和 Codex 的配置概念按语义关系处理。语义不同的地方保留差异并报告风险，
只同步可以解释清楚的部分。

分发目标是插件自带 skill 与工具映射知识，再配一个很薄的包装脚本。用户安装插件后，
即可在对应工具中调用这些能力。

## 产品约束

1. **规范源优先**。目标工具配置文件可以由规范源生成，也可以作为采纳输入；采纳后仍回到规范源。
2. **写入前先出计划**。任何写入前都要展示将创建、更新、跳过、阻塞或冲突的内容。
3. **冲突不自动合并**。规范源和目标工具投射结果相对上次同步态同时变化时，工具报告
   `conflict`，由用户选择处理方式。
4. **按语义映射**。Claude 提示词规则、Codex 项目指令、Codex 命令审批规则分属不同语义，
   只同步语义等价的部分。
5. **写入可追溯**。投射与采纳都通过 git 留痕：`git diff` 展示精确变更，git 历史提供
   上次同步基线，必要时可以回滚；采纳需要说明目标工具中的修改为什么可以进入规范源。

## 成功标准

MVP 达标时，用户新增或修改一个项目技能，只需要修改规范副本，Claude Code 和 Codex
都能看到各自可用的投射结果。

项目说明和规则也应只有一份主要来源。`CLAUDE.md` 与 `AGENTS.md` 可以由工具生成或更新；
如果用户手工改了受管内容，工具能报告漂移，并在无冲突时采纳回规范源。

钩子的成功标准是工具能清楚说明哪些意图可以完整映射，哪些只能部分映射，哪些必须人工
处理。
