# 技术栈与依赖选型

## 设计取向

Bridge 的能力默认通过 skill 调用目标工具和 LLM 的固有能力，只有过了一道窄门才写代码：

- **默认走固有能力**：文件读写交给目标工具自带的 Read / Edit / Write，语义判断交给 LLM。
- **窄门才写代码**：一个操作同时满足“交给 LLM 做费 token”和“用代码实现是小轮子（极简、
  稳定、不随工具语义变）”时，才写死成代码——例如逐字节比对、已确定映射的查表。
- **确定性底座**：变更判断、基线和回滚交给 git。

判据落在“是否在重复造已有的大轮子”，而不是“代码越少越好”；代码面因此自然收窄。

## 主要构成

| 层面 | 用途 | 选定 |
| --- | --- | --- |
| skill 内容 | 投射 / 对账工作流与护栏 | 面向目标工具中智能体的 skill（markdown + frontmatter） |
| 工具映射知识 | Claude / Codex 语义差异（`full` / `partial` / `unsupported`） | 已确定映射作枚举表，长尾用自然语言知识库，带采集日期 |
| 规范源格式 | 规范条目，便于人工审阅和目标工具中的智能体处理 | markdown + 轻量 frontmatter，加目录约定 |
| 确定性底座 | 变更检测、上次同步基线、回滚 | git（`diff` / 历史 / `restore`） |
| 文件读写 | 读取现状、写入受管区块 | 目标工具自带 Read / Edit / Write |
| 输出稳定性 | 减少无意义 diff，保护人工内容 | 受管区块标记 + 落盘前逐字节比对 |
| 包装脚本 | 定位自带文件、过窄门的确定性操作、doctor | 包装脚本 |
| 运行时 | 包装脚本运行时（如需要） | Node.js >= 20 LTS |
| frontmatter / YAML | 解析 skill / 规范条目元数据 | `yaml`（仅在包装脚本确有解析需求时引入） |

## 能力归属

按上面的判据，操作分到三处：

- **目标工具自带工具**：读取现状、写入受管区块；编码、行尾、原子写已经做好，不重写。
- **代码（过窄门的）**：逐字节比对、空 diff 归一化、已确定映射的枚举表，以及批量
  frontmatter 解析。
- **LLM / skill**：尚未沉淀的映射、冲突仲裁、从自然语言起草意图。

git 承担变更检测、基线和回滚；规范源用 markdown，不先引入完整 schema 校验层。

## 依赖边界

- **用户机前置**：git 必装；Node.js 仅在包装脚本需要时作为运行时。
- **开发期**：文档与 skill 以文本为主；如果包装脚本使用 TypeScript，再引入最小 dev
  工具链（类型、打包、测试）。
- **运行期依赖**：默认只依赖 git 和目标工具能力；frontmatter 解析仅在包装脚本确有需要时
  引入 `yaml`。
