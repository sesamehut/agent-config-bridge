## 收口摘要

上一节是计划口径的交付项，本节是收口时记录的设计结论与边界：

- 一个 `plugin/` 目录同时是两个 host 的插件根：两个 host 都静默接受对方的
  manifest 目录，`skills/`、`templates/`、`knowledge/` 保持上游的兄弟布局，
  skill 正文逐字节拷贝，不按 host 渲染，也不引入任何 `${CLAUDE_*}` 占位符
  （Codex 不做替换，Claude 即使没有占位符也会告知技能基目录）。
- 产物相对上游只有两处改写：`knowledge/*.md` 中 `](../docs/` 改为本仓库
  GitHub `blob/main` 地址并把显示文本的 `../` 去掉；`agents/openai.yaml` 的
  `default_prompt` 把 `$bridge-*` 改成 `$agent-config-bridge:bridge-*`。后者
  已由 Codex 实机会话证实：模型看到的技能名就是
  `agent-config-bridge:bridge-sentinel` / `agent-config-bridge:bridge-sync`。
- `allowed-tools: Read` 是 M5 内必须做的决定而不是推迟项：不声明时，Claude
  从会话 cwd 之外的插件缓存读取自带 references / templates / knowledge 会被
  拒绝。只放开只读工具；带路径的 `Read(<path>)` 因单斜杠、双斜杠与 Windows
  盘符的锚定规则跨平台不一致而不采用；自带 Python 脚本仍走 Bash 权限确认，
  `claude -p` 非交互运行需要用户自己给 `--allowedTools`。
- `bridge-sync` 保持 `policy.allow_implicit_invocation: true`：写侧技能只在
  用户确认完整计划后落盘，隐式调用不改变这一点；两个 host 都不能单独关掉一个
  插件 skill，README 已告知只能整体禁用或卸载。`disable-model-invocation`
  会被 Codex 官方 `validate_plugin.py` 拒绝，不是可选项。
- 市场清单放在仓库根是 Codex 侧唯一的安装路径（Codex 没有 `--plugin-dir`，
  CLI 子命令也不自动发现仓库根市场）；登记到外部市场仍按分发模型推迟。
- manifest 的 author / owner 沿用公开仓库 `appstore-connect-skill` 的作者
  身份；仓库没有 LICENSE，manifest 省略 `license` 字段，产物不带 LICENSE。
- 0.1.0 产物冻结的契约 tuple 是 `covenant/v3`、`source-tree/v5`、`report/v5`、
  `reconciliation/v3` 与 `sync-plan/v3`，与 [M4 收口记录](m4.md)一致。
- 已知的产物文字偏差：哨兵 description 末尾的「validate bridge fixtures」与
  `bridge-sync` Procedure 第一步「refuse to run with cwd inside `fixtures/`」
  指的是本仓库的夹具，而夹具不随产物分发；两处都不影响运行，记录为已知偏差，
  不在 M5 用改写掩盖。

需要 host 在本机的只读校验（不写用户配置；自动化消费者只把退出码 0 视为通过，
`plugin details` 对不存在的插件也返回 0，因此要对它的输出做字面断言）：

```text

claude plugin validate ./plugin --strict
claude plugin validate ./plugin/skills --strict
claude --plugin-dir ./plugin plugin details agent-config-bridge   # 断言输出含 "Skills (2)  bridge-sentinel, bridge-sync"
PYTHONUTF8=1 python -B ~/.codex/skills/.system/skill-creator/scripts/quick_validate.py plugin/skills/bridge-sentinel
PYTHONUTF8=1 python -B ~/.codex/skills/.system/skill-creator/scripts/quick_validate.py plugin/skills/bridge-sync

codex plugin marketplace list --json -c 'marketplaces.agent-config-bridge.source_type="local"' -c 'marketplaces.agent-config-bridge.source="<仓库根，正斜杠>"'
codex plugin list --available --json -c 'marketplaces.agent-config-bridge.source_type="local"' -c 'marketplaces.agent-config-bridge.source="<仓库根，正斜杠>"'   # 断言出现 agent-config-bridge@agent-config-bridge
```

`-c` 覆盖只对该次调用生效，两条 Codex 命令都要带同一对覆盖。Windows 默认

证据边界：

- 上述检查证明的是产物字节、两侧校验器与本机一次可逆的安装 / 卸载；不证明任何
  用户机器上的安装体验，也不证明技能在真实项目里的运行结果。
- GitHub 安装路径未验证：产物尚不在默认分支上，也没有发布 tag，`owner/repo`
  简写会解析到没有 `plugin/` 的 `main`。README 因此要求带 `#<ref>` / `--ref`，
  收口只验证了本地检出路径。`--sparse` 双路径形式两侧都未实测。
- 知识库链接钉在 `blob/main`，随主分支漂移；改为按发布 tag 钉住留待 M6 建立
  tag 流程时处理。
- `claude plugin tag`、CI 门禁与外部市场登记属于 M6 或之后；`allowed-tools`
  只放开 Read，Bash 预授权仍是推迟项。
- 本机 `python3`（pyenv 3.12.9）与 `python`（3.14.5）是不同解释器，文档只给
  探测顺序，不写死解释器名。
- M4 收口记录里的 Codex `/hooks` 交互式信任会话仍未完成，本里程碑不改变其
  状态；插件本身不分发 hook。
- 仓库没有 LICENSE、manifest 作者身份与外部市场登记是用户决定项，收口记录
  只记录当前选择。
